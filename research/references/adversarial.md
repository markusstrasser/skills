# Adversarial Review

Use for `--adversarial` or a request to challenge, debunk, stress-test, or "call BS on" a claim, intervention, field, or result. The question is: what is the strongest evidence that this is wrong, noise, or explained by something else, and does that critique survive scrutiny? Broad adversarial reviews normally need Deep scope; a bounded single-claim check can stay bounded.

## Build and test the case

1. State the target claim and steel-man why serious people believe it. Distinguish the strongest version from an easy caricature.
2. Choose the relevant attack directions: replication status, strongest critic, alternative explanation, methodological failure, or disagreement among meta-analyses. A field without meta-analyses does not require a fruitless search for them.
3. Search for evidence and mechanisms, not only rhetorical criticism. Inspect the strongest rebuttal to the critique as well as the strongest evidence for it.
4. Verify the critique itself: source identity, numbers, population match, selective counter-evidence, overclaiming, and contrarian bias. Apply the same evidence standards to congenial and hostile results.
5. Explain what survives and what the data support instead. A constructive null is better than a list of objections.

For broad adversarial work, use the relevant examples in [the case library](/Users/alien/Projects/agent-infra/research/adversarial-case-library.md) and the matching domain query patterns in [DOMAINS.md](../DOMAINS.md). The case library's quality markers are evidence over rhetoric, a seriously believed target, structural critique, informed critics, engagement with rebuttals, and a constructive alternative. A critique's being unanswered is a finding to verify, not a quality guarantee.

Example query framings: "strongest case that X is noise", "celebrated Y finding failed to replicate", or a domain-specific failure mechanism. Refine these from actual sources rather than issuing every framing by default.

## Case brief

Label the result an adversarial brief. Use the structure below when helpful; a single claim may need only a few paragraphs.

```markdown
## Adversarial Review: [Target]

**Target claim:** [what is challenged]
**Prior belief:** [why serious people believed it]
**Date:** YYYY-MM-DD

### The Case Against
[Evidence with sources, effect sizes, and relevant limitations]

### Strength Assessment
| Criterion | Assessment | Evidence |
|---|---|---|
| Evidence quality | HIGH / MED / LOW | [specific] |
| Target seriously believed | YES / NO | [by whom] |
| Structural critique | YES / NO | [mechanism] |
| Rebuttals addressed | YES / NO / NOT FOUND | [what was checked] |
| Constructive null | YES / NO | [alternative explanation] |

### What Survives
[Claims and qualifications that withstand scrutiny]

### Verdict
[Demolished / mortally wounded / weakened / survives with caveats / critique fails]

### Sources & Search Log
[Provenance, access limits, and search/verification record for Deep reviews]
```

The verdict label summarizes the evidence; it is not a target to attain. Stop when the material resolves the challenge or further searches repeat it. Report an unresolved case instead of manufacturing a decisive conclusion.
