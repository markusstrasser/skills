# Gap and Novelty Audits

Use for “what have we not researched/mined yet?”, “what is missing?”, or “why did the scout miss this?” in research intended to feed a repository or operational system. A keyword, paper title, lever name, or broad backlog row is not evidence of coverage.

Build a compact coverage matrix across the requested surfaces, such as architecture, objective, loss, optimization, interpretability, data, ontology, and language. Grade each direction `DONE`, `QUEUE`, `FAILED`, `CONDITIONAL`, or `GAP` from live evidence.

A direction counts as covered only when these are identifiable:

1. Input/output contract, including uncertainty or abstention states.
2. Mechanism or state transition, not merely a topic or name.
3. Live consumer and repository destination.
4. Cheapest discriminating gate and held-out principal metric.
5. Relation to prior work: consumes, supersedes, failed-at, or reopens-if.

If a local direction lacks one of these, classify it as an underspecified queue/gap. Search using the missing mechanism language, for example “partial AST realizability”, “ontology revision after empty version space”, or “multiple-hypothesis data association”. Do not restrict discovery to the repository's nouns.

Route each genuine implementation gap to an existing consumer or a concrete dependent obligation. An interesting concept without a consumer is a lead, not an implementation finding. In the closeout, explain why the previous process missed each survivor and identify the smallest durable repair that would catch the class. Apply a repair only within the user's authorized scope.

For a pure literature question, use the same distinction between named topics and demonstrated coverage without inventing a repository consumer or benchmark the user did not request.
